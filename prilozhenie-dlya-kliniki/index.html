Приложение для клиники: от выбора времени до подтверждённой записи

Начните с одного пути пациента: выбрать время и увидеть тот же подтверждённый визит, который видит регистратура. Ниже — модель приложения, границы обмена с МИС и проверки, по которым можно оценить первую версию.

Редакция BORNLI · 2026-11-05

До разработки

Проверьте существующую запись с телефона.

Возьмите один маршрут: выбрать филиал и специалиста, записаться, затем найти свой визит. Попросите администратора показать эту же запись в медицинской информационной системе — МИС. Запишите, где пациенту приходится звонить, возвращаться на сайт или повторно вводить сведения. Это даст требования к приложению.

В руководстве МедТочки, страницы 20–23, уже описаны просмотр созданной записи, её перенос и отмена. Перед заказом своего продукта проверьте доступные функции вашей МИС и подключённого кабинета. Если они закрывают маршрут, начните с настройки существующего решения. Свой интерфейс имеет смысл обсуждать, когда остаётся конкретная задача: например, единый выбор времени по нескольким филиалам.

Модельный сценарий

Пациент выбрал 16:00. Кто подтвердил запись?

Представим сеть с двумя филиалами. Пациент выбирает Северный филиал, консультацию и 12 ноября, 16:00. Дата, филиалы и номера в этом примере условные. На экране выбора показываем «Запись ещё не создана». Доступное время нужно повторно проверить при отправке запроса: пока человек читал карточку, администратор мог занять это окно.

Предлагаем разделить три состояния. «Выбрано время» означает действие на телефоне. «Проверяем запись» означает отправленный запрос. «Запись подтверждена» показываем после того, как МИС вернула номер созданного визита. Если ваша система принимает только заявку для последующей обработки регистратурой, экран должен прямо говорить «Ожидает подтверждения». Этот вариант нельзя изображать как готовую запись.

При занятом окне приложение сохраняет выбранные филиал и услугу, обновляет расписание и предлагает доступные варианты. В модели пациент выбирает 16:30. Автоматически записывать его на другое время не следует.

Обмен с МИС

Телефон потерял ответ. В расписании остаётся один визит.

В нашем примере МИС создала запись A-024 на 16:30, но подтверждение не дошло до телефона. Повторное нажатие не должно занимать ещё одно окно. Для этого в проекте нужно согласовать идентификатор операции и способ найти её результат. При повторе сервер возвращает существующую A-024. Такой сценарий проверяют с конкретной МИС: наличие API само по себе не подтверждает, что повтор обработается правильно.

Пока результат неизвестен, покажите «Уточняем статус» и способ связаться с регистратурой. Администратору нужны номер запроса, филиал, время и история обмена. Он должен отличать неотправленную заявку от уже созданного визита. В журнал не нужно копировать всю медицинскую карту ради поиска записи.

Перенос — отдельная операция. Если МИС поддерживает безопасное изменение времени, используйте её штатный механизм. Если перенос состоит из отмены и новой записи, заранее разберите сбой между этими действиями. Пациент должен видеть, сохранился ли прежний визит, а администратор — незавершённую операцию. Нельзя обещать успешный перенос только потому, что новое время появилось на экране.

Границы первой версии

Запись на приём и медицинская карта требуют разного объёма работы.

Для первого прототипа достаточно расписания, создания записи, её состояния и контакта регистратуры. Используйте вымышленные данные. Выдачу результатов исследований, семейные профили и медицинские документы вынесите в отдельный объём: для каждого понадобится определить, кто и на каком основании получает доступ.

До разработки согласуйте с клиникой и её специалистами по защите данных состав сведений, хранение, сроки удаления, согласия и права сотрудников. Эти решения зависят от устройства сервиса; макет не подтверждает соответствие требованиям. Для уведомления на заблокированном телефоне предлагаем нейтральный текст «Обновилась ваша запись», а подробности — после входа в приложение. Проверьте также, что после выхода из одного аккаунта следующий пользователь устройства не видит его визиты.

Приёмка и оценка

Пять проверок вместо списка красивых экранов.

  1. Окно заняли одновременно. Два тестовых пользователя выбирают одно время. Подтверждение получает только тот, чья запись создана в МИС; второй видит актуальные варианты.
  2. Ответ потерялся после создания. Повторите ту же операцию. Администратор находит один визит, пациент получает его номер.
  3. Изменилось расписание. Уберите выбранное время до подтверждения. Старое окно не должно остаться доступным для оформления.
  4. Перенос прервался. Остановите обмен между шагами. В интерфейсах пациента и администратора видны фактический визит и задача для восстановления.
  5. На телефоне сменился аккаунт. Проверьте прежние экраны, уведомления и переход по старой ссылке. Данные первого тестового пользователя второму недоступны.

Для оценки подготовьте название и версию МИС, описание доступного обмена, правила записи и переноса, список филиалов и обезличенный пример проблемной операции.
